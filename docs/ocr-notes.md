# Разбор структуры документа: как устроено и где ломается

Про качество разбора старых технических справочников: плотная двухколоночная
вёрстка, таблицы **без единой линейки**, колонки держатся на выравнивании
пробелами. Всё, что здесь записано, измерено на `bench/tables20.pdf` — 20
страниц, 22 таблицы, 195 непустых ячеек по эталону Mistral OCR.

## Тракт целиком

```
PDF --рендер 2.0 (144 dpi)--> 1012x1466
    --Resize 800x800, keep_ratio: false--> детектор PP-DocLayoutV2 (ONNX)
    --рамки--> постобработка (порог, NMS, вложенность, unclip, порядок)
    --filter_overlap_boxes--> кроп по рамке БЕЗ полей
    --сжатие до 1 Мпикс, JPEG 75--> VLM 0.9B, промпт "Table Recognition:"
    --OTSL--> convert_otsl_to_html --> HTML внутри Markdown
```

Модель возвращает **OTSL**, не HTML и не Markdown: шесть тегов
`<fcel> <ecel> <nl> <lcel> <ucel> <xcel>`. Промпт — ровно два слова, без
системного сообщения и без указания формата. Если ответ не OTSL, конвертер
отдаёт пустую строку и в документ уходит сырой текст. У нас таких случаев
ноль: **если рамку дали, таблица получается всегда**.

## Корень: детектор видит страницу сплющенной

`~/.paddlex/official_models/PP-DocLayoutV2_onnx/inference.yml`:

```yaml
Preprocess:
- interp: 2
  keep_ratio: false      # пропорции НЕ сохраняются
  target_size: [800, 800]
```

Вход ONNX-графа объявлен жёстко: `image [N, 3, 800, 800]`. Настроить нельзя —
обе доступные модели перечислены в `STATIC_SHAPE_MODEL_LIST`, попытка задать
`img_size` роняет assert, а сам пайплайн отдельно запрещает третью модель:
`assert model_name in ["PP-DocLayoutV2", "PP-DocLayoutV3"]`.

Страница 1012x1466 сжимается по горизонтали в 0.79, по вертикали в **0.55**.
Межстрочный интервал — единственный признак, по которому строка таблицы без
линеек отличается от строки абзаца, — страдает сильнее всего.

Поднимать `PADDLE_PDX_PDF_RENDER_SCALE` ради детекции **бесполезно**: всё
равно упрётся в 800x800. Это влияет только на качество кропа для VLM.

не найдено»:

|---|---|---|---|
| 300 | [525,676,900,786] | `text` 0.95 | 98 % |
| 301 | [531,1109,908,1257] | `text` | 96 % |
| 314 | [525,1131,901,1217] | `text` | 97 % |
| 298 | [131,1226,501,1292] | `display_formula` | 92 % |

**Это ошибка классификации, а не локализации.** Геометрия уже правильная.

## Три независимых предохранителя, гасящих таблицу

Каждый по отдельности разумен, все три бьют по одному классу документов.

**1. NMS, `iou_diff=0.98`** (`object_detection/processors.py:613`). Рамка гасит
рамку *другого* класса при перекрытии 0.98. Текстовая 0.95 поверх табличной
0.49 перекрывается ровно настолько.

**2. Вложенность, `layout_merge_bboxes_mode`** (`layout_analysis/processors.py:835`).
В конфиге 1.6 классам `chart`, `display_formula`, `doc_title`,
`inline_formula`, `paragraph_title` присвоен режим `large`: любая рамка, чья
площадь на >= 90 % внутри такой рамки, удаляется молча (`is_contained`,
iou >= 0.9). На **фрагменте** страницы заголовок занимает вчетверо большую
долю площади и съедает таблицу целиком.

**3. `filter_overlap_boxes`** (`paddleocr_vl/uilts.py:108`). При перекрытии
больше 0.7 есть защиты для пар вроде {table, image}, а пара {table, text}
проваливается мимо них — побеждает рамка с большей площадью, то есть текстовая.
Правится в `entrypoint.py::_prefer_tables_over_text`.

## Замеры

Максимальная уверенность класса `table`, локальный стенд без GPU:

| стр | вся страница | лучший кусок | зеркало |
|---|---|---|---|
| 300 | 0.055 | **0.489** | — |
| 305 | 0.176 | **0.612** | 0.301 |
| 302 | 0.197 | 0.099 | **0.419** (верт.) |
| 301 | 0.196 | 0.148 | **0.348** (гориз.) |
| 311 | 0.389 | **0.809** | — |

Ни один взгляд не выигрывает у остальных — они вытаскивают разные страницы.
Объединение при пороге 0.30: **19 рамок из 22 против 7 у полной страницы**, при
нуле ложных срабатываний на четырёх пустых страницах.

Отражения работают потому, что детектор судит о табличности по геометрии
белого, а не по чтению текста: страница вверх ногами ему не мешает, а сдвиг
пиксельной сетки перебрасывает пограничный случай через порог. Поворот на 90°,
наоборот, обнуляет всё — модель жёстко привязана к вертикали.

## Что проверено и отвергнуто

**`PP-LCNet_x1_0_table_cls`** — непригоден. У него два класса, «wired» и
«wireless»; сказать «это не таблица» он не может и уверенно называет таблицей
любой абзац (15 из 15).

**`SLANeXt_wireless`** — не стоит. 143 ячейки против 176 у детектора ячеек,
при 11.9 с/кроп вместо 2.0.

**`RT-DETR-L_wireless_table_cell_det`** — годится, но не «вторым мнением»: там,
где мы справляемся, выигрыша нет. Ценность в роли **ворот**: кластеризация
найденных ячеек по колонкам даёт >= 3 колонок у 18/18 таблиц и 0/15 абзацев.
Идеальное разделение. Отдаёт только геометрию, текст всё равно за нашей VLM.

**Пороги детекции для прочих классов.** Понижение всех 25 классов до 0.3
вместо штатных 0.5 **уменьшило** число сырых рамок `table` с 20 до 17: выживает
больше текстовых рамок, и часть таблиц гасится на NMS.

**`merge_layout_blocks=False`.** Описание параметра дословно совпадает с нашим
симптомом («склейка боксов через колонки»), но таблицы из этой склейки
исключены по построению: `merge_blocks(..., non_merge_labels=image_labels + ["table"])`.

## Мелочи, стоящие внимания

- Комментарии к списку классов в `PaddleOCR-VL-1.6.yaml` **врут** (там
  `9: footer`, `13: header`, `23: text`). Настоящие метки — в `label_list`
  весов. Индекс 21 = `table` верен в обоих вариантах.
- При ONNX Runtime детектор не отдаёт масок, и `layout_shape_mode`
  принудительно вырождается в `"rect"`. Полигональные ветки — мёртвый код.
- Пайплайн понижает `max_new_tokens` до 4096, тогда как в константах модели
  8192. Обрыв на длинной таблице даёт рваный OTSL, а `otsl_pad_to_sqr_v2`
  затем **молча обрезает** строки длиннее «оптимальной ширины».
- Кроп режется ровно по рамке, без полей (`layout_unclip_ratio` = `[1.0, 1.0]`).
- Кроп уезжает на сервер как JPEG качества 75, настройки нет.

## Калибровка ожиданий

На бенчмарке из реальных книг (Dr. DocBench, 4514 страниц) лучшая в мире
система даёт TEDS **55.85**, а не 94, как на OmniDocBench. PaddleOCR-VL-1.6
занимает первое место по Table TEDS (94.76); Mistral OCR по той же метрике даёт
**76.78** — он слабее в распознавании, но у него нет стадии, где таблицу можно
потерять из-за неверной рамки.

Мы вытаскиваем около 55 % ячеек. Это не провал ниже уровня техники — это
примерно он и есть.

## Главный поворот: содержимое не терялось

Постраничное сравнение с эталоном (`tools/tabcmp.py`) показало, что «потерянные»
таблицы на самом деле разобраны — но записаны как обычный текст. Страница 309,
где у нас числился ноль таблиц:

    Tool Room  12" to 18" inc.  20" to 36" inc.
    Lathe  Engine Lathe  Engine Lathe
    0 to (±).0003"  0 to (±).0005"  0 to (±).0008"

Эталон Mistral на том же месте даёт то же самое, только с палками. Дюймовые
штрихи мы читаем вернее (`"` против его `'`), а на стр. 311 у него в заголовке
«Pool Room Lathes» вместо «Tool». Эталон не безгрешен.

По всем 22 эталонным таблицам: содержимое цело у 6, частично у 14, потеряно у 2.
«Частично» почти везде — один и тот же артефакт: Mistral склеивает перенесённый
заголовок в одну ячейку, мы держим его двумя строками. Обе записи законны.

Вывод, меняющий план работ: детектор ставит рамку правильно и отдаёт кроп в VLM,
а та, получив ярлык `text`, честно читает строки вместо построения сетки. Ломается
не детекция, а одно решение о разметке в самом конце. Чинится переспросом той же
VLM по тому же кропу с табличным промптом — без единой новой модели. RT-DETR при
таком раскладе не нужен.

## Замер olmOCR-2-7B

| прогон | таблиц из 22 | ячеек (эталон 195) | страниц точно как в эталоне |
|---|---|---|---|
| PaddleOCR базовый (`tables-min2`) | 12 | 123 | 5/20 |
| PaddleOCR + взгляды (`tables-mv3`) | 14 | 160 | 6/20 |
| olmOCR без правок (`olmocr`) | 19 | 196 | 8/20 |

47 с на 20 страниц, $0.083 за прогон с арендой, завёлся с первой попытки —
опасение о несовместимости vLLM 0.27.1 с этой моделью не подтвердилось.

Два изъяна, которых не видно в сводных числах:

- **Сетка едет.** Стр. 309 — пять столбцов вместо трёх, перенесённый заголовок
  растащен по лишним колонкам. Стр. 318 — сдвиг на позицию: в трёхколоночной
  таблице строка из четырёх значений. У PaddleOCR на тех же страницах сетка чистая.
  Поэтому «196 против 195» модели льстит: лишние ячейки от кривой сетки считаются
  наравне с верными. Число ячеек — не мера качества.
- **Рисунков нет вовсе.** Разбор 68 КБ против 1.3 МБ, каталога `imgs` нет,
  34 вынутых рисунка против нуля.

Итог: тезис «двухстадийная схема и есть источник проблемы» подтверждён — модель
без детекции и без настройки обходит месяц заплаток. Но замена не прямая.
Запасной путь, если переспрос не выйдет: разбор от olmOCR, рисунки от детектора
макета отдельно — блоки `image` он находит с уверенностью 0.97–0.99 и здесь не
ошибается.

## Переспрос: 21 таблица из 22

Проверка диагноза «ломается ярлык, а не детекция». Блоку `text`, похожему на
таблицу, меняется ярлык на `table` сразу после нарезки кропа и до склейки
соседних блоков (в `merge_blocks` есть `non_merge_labels=[... "table"]`, так
что переименованный кандидат перестаёт приклеиваться к абзацу сверху). Дальше
пайплайн сам шлёт тот же кроп в ту же VLM с промптом `Table Recognition:`.
Ни одной новой модели.

Геометрия только отбирает кандидатов, и намеренно щедро: замер ширин просветов
между столбцами дал 22..110 px у настоящих таблиц против 20..35 px у обычных
абзацев — диапазоны перекрываются, порога не существует. Подбирать его было бы
ровно тем перебором микропараметров, который здесь ничего не решает.

Решение выносит модель, и её ошибка обратима: вырожденная сетка (меньше двух
столбцов или меньше двух строк) разворачивается обратно в текст, содержимое при
этом цело — оно лежит по ячейкам (`_unwrap_degenerate_tables`).

| прогон | таблиц | ячеек (эталон 195) | прозы испорчено | слов |
|---|---|---|---|---|
| база (`tables-min2`) | 12 | 123 | 0 | 9995 |
| взгляды (`tables-mv3`) | 14 | 160 | 0 | 10018 |
| olmOCR (`olmocr`) | 19 | 196 | 0 | 10073 |
| переспрос (`tables-reask`) | 20 | 228 | 0 | 9998 |
| переспрос + взгляды (`tables-both`) | 22 | 242 | 0 | 10019 |

Из 24 переспросов 8 развернулись обратно. Ложных таблиц на четырёх пустых
страницах ноль во всех прогонах.

Число «22» надо читать честно: это 21 настоящая таблица плюс один обрывок на
стр. 320 (`.003" | .003" | (Bar test 3" from end of jaw...)`) — вторая рамка
накрыла тот же участок. Стр. 304 не взята никем из наших прогонов: содержимого
нет ни в одном, рамки нет вовсе.

Два оставшихся промаха — другой болезни. На стр. 317 рамка захватила один
столбец из трёх (`Tool Room / Lathe / .0008"`), модель честно построила таблицу
в одну колонку, и разворот вернул её в текст. Это промах локализации, против
него переспрос бессилен по устройству — и именно его закрывают взгляды.

Поэтому взгляды остаются: они дают +1 настоящую таблицу (стр. 317, ровно 18
ячеек как в эталоне) ценой 12 % времени разбора (27 с против 24 с на двадцати
страницах). Раньше они выглядели дорогой подпоркой, потому что лечили не ту
болезнь; после переспроса у них осталась одна узкая задача, которую больше
закрыть нечем.

## Проверка на отложенной выборке

Пороги ворот подбирались, глядя на те же двадцать страниц, на которых потом и
мерилось, — подгонка под тест. Поэтому собрана вторая выборка из страниц,
которых я не видел: 4, 40, 143, 292, 393..400, 443..450 (`bench/holdout20.pdf`,
список страниц рядом в `.pages.json`). Четырнадцать страниц из двадцати без
таблиц вовсе — для проверки на ложные срабатывания. Таблицы другой формы:
двухколоночные допуски, трёхколоночные с пустыми ячейками в шапке, оглавление
с точечными выносками. Прогон без единой правки настроек.

| | результат |
|---|---|
| эталонных таблиц | 8 |
| содержимое цело | 8 из 8 |
| размечено таблицей | 6 из 8 |
| ложных таблиц на 14 пустых страницах | 0 |
| переспросов отвергнуто и развёрнуто обратно | 20 из 20 |
| прозы, испорченной в таблицу | 0 |

Ворота не оказались подогнанными: на формах таблиц, которых они не видели,
работают так же. Стр. 397 и 447 взяты полностью (2 из 2 на каждой).

Два расхождения, оба поучительные:

- **Стр. 4** — оглавление. Mistral размечает его таблицей на 66 ячеек, мы —
  списком с выносками. Содержимое цело, и список здесь полезнее таблицы;
  считать это промахом нельзя.
- **Стр. 40** — маленькая таблица размеров получила ярлык `display_formula`
  с уверенностью 0.95, и VLM честно отдала её массивом LaTeX. Содержимое цело,
  разметка неверна. Это новый разряд промаха: наши ворота смотрят только на
  блоки `text`. Расширять их на `display_formula` рискованно — разворот
  вырожденной сетки вернёт настоящую формулу простым текстом и потеряет LaTeX;
  здесь нужен другой предохранитель, а не тот же.

## Насколько разбор точен в абсолютных величинах

Эталона нет ни у кого, поэтому меряем тройкой независимых свидетелей: наш
разбор, Mistral и собственный текстовый слой PDF (старый OCR издателя).
Там, где двое согласны, а третий расходится, ошибается почти наверняка третий
(`tools/tri.py`).

| | слов из согласованных | своих слов, которых нет ни у кого |
|---|---|---|
| наш | 99.4 % | 46 |
| Mistral | 99.9 % | 225 |
| слой PDF | 95.8 % | 604 |

225 «своих» слов Mistral — это на 136 кусков имён файлов `img-347.jpeg`, то есть
не текст. Наши 46 разбираются так: `circ`, `array`, `begin`, `cccc` — обломки
LaTeX; `laihes`, `tarsock`, `piaced`, `mch` — настоящие ошибки чтения. Итого
около 12 неверно прочитанных слов на 10 100, то есть ~0.15 %.

Для книги допусков решают числа, и они считаются отдельно (колонцифры
исключены — мы срезаем их нарочно):

| | чисел из согласованных | выдумано |
|---|---|---|
| наш | 98.7 % | 10 |
| olmOCR | 94.4 % | 64 |

Все шесть недостающих чисел — перекрёстные ссылки (`15.11`, `26.61`, `26.74`,
`12`, `1`, `1`). **Ни одно значение допуска не потеряно.** У olmOCR выдуманных
чисел в шесть раз больше — на такой книге это дороже, чем его преимущество в
поиске таблиц.

Вывод для доверия: читать и искать по разбору можно без оригинала. Брать из
него значение допуска и по нему работать — пока нет, и не из-за величины
ошибки, а из-за её молчаливости: десять выдуманных чисел на двадцать страниц
ничем не помечены.

Лечится это дешевле, чем переобучение: числа сверяются с текстовым слоем PDF,
совпало — принимаем, есть только у нас — помечаем. Очередь на проверку выходит
10 мест на 20 страниц, то есть около 270 на всю книгу.

## Разрешение подачи: мы сами уменьшали картинку

В PDF лежит скан 4222 x 6112 px (600 dpi). Пайплайн рендерит страницу с
`PADDLE_PDX_PDF_RENDER_SCALE` = 2.0, то есть 1012 x 1466 (144 dpi) — вчетверо
меньше по стороне.

Хуже того, у VLM есть нижний порог входа `min_pixels` = 112896. Табличный кроп
при таком рендере это 375 x 66 = 24750 px, вчетверо ниже порога, и пайплайн
растягивает его интерполяцией. Цифры допусков модель читает из размазанного
огрызка, хотя оригинал вчетверо резче.

Замер на 288 dpi (`bench/tables-hi`, переменная проброшена через env задачи):

| | чисел из согласованных | выдумано |
|---|---|---|
| 144 dpi (`tables-both`) | 98.7 % | 10 |
| 288 dpi (`tables-hi`) | 98.9 % | 6 |

Таблиц в обоих 22, прозы не испорчено, объём текста тот же. То есть рычаг
настоящий, но скромный: выдуманных чисел на 40 % меньше, общая точность почти
не двинулась. Дороже прогон на 20 % (29 с против 24 с).

Прогон вскрыл ошибку в воротах: порог ширины просвета стоял в пикселях (12) и
молча разъезжался при смене разрешения — на 288 dpi просветы вдвое шире, порог
стал вдвое мягче, и на переспрос ушло 103 блока вместо четырёх. Разворот их
вернул и ничего не испортил, но 99 вызовов VLM пропали зря. Теперь порог
меряется в долях высоты строки: 34 срабатывания на 144 dpi против 35 на 288.

## Можно ли доверять таблицам: замер по строкам значений

Число ячеек ничего не говорит о том, попало ли значение в свой столбец.  Для
разбора, который дальше пойдёт в модель-пересказчик, важно именно это: человеку
столбец подсказывает вёрстка, модели — только разметка.  `tools/gridcmp.py`
сверяет строки значений: та же тройка чисел в том же порядке.

Из 29 строк значений эталона точно воспроизведены 20 (69 %).  Разбор всех
девяти расхождений:

- **2 — ошибка Mistral, а не наша** (стр. 314): он прочёл `(1)` и `(2)` там,
  где стоит `(±)`; текстовый слой PDF подтверждает нас.
- **1 — лишняя кавычка** (стр. 311), косметика.
- **1 — потерян знак `±`** (стр. 303): `0 to .0005"` вместо `0 to (±) .0005"`.
  Смысл меняется.
- **1 — НЕВЕРНОЕ ЗНАЧЕНИЕ** (стр. 304): у нас `.0005`, на скане третий столбец
  начинается на `.001` (Mistral даёт `.0015`).  Скан в этом месте выцвел, и
  модель дописала третий столбец по образцу первых двух.  Это характерный
  порок VLM: на неразборчивом входе она продолжает узор, а не сомневается.
- **4 — стр. 313**, где детектор выдал табличную рамку `[116, 1256, 917, 1344]`
  шириной 801 px на странице в 1012 px, то есть поперёк межколонника.  Две
  разные таблицы склеились в одну сетку на 10 столбцов, и «Engine Lathe»
  оказался в столбце значений.

Рамка поперёк межколонника есть и в базовом прогоне `tables-min2` — это порок
самого детектора, а не взглядов; я сперва подумал на них и ошибся.

Для пересказа и перевода это значит: проза безопасна, качественные утверждения
о таблицах безопасны, конкретное значение допуска брать нельзя.  Худший из
дефектов — именно склейка поперёк колонок: модель-пересказчик получит уверенную
чепуху, а не пропуск.

## Механизмы уверенности: что работает, а что нет

Наш худший порок — молчаливость: на выцветшем скане (стр. 304) модель дописала
третий столбец по образцу первых двух и выдала `.0005` вместо `.0015` с тем же
видом уверенности.  Проверены два способа заставить её признаться, оба без
единой новой модели.

### Вероятности токенов

vLLM отдаёт logprob каждого токена, если попросить: `logprobs=True` в запросе.
Патчится `GenAIClient.create_chat_completion` и `_doc_vlm_genai_collect_responses`
(там лежат целые объекты ответа, а не только текст).  Токены с logprob ниже -1.0
(~37 % вероятности) помечаются в разметке: ячейка целиком через `⚠`, кусок прозы
через `<mark>`.

Результат: помечены 5 ячеек, **все пять — настоящие ошибки чтения** (`(m.c.`
вместо `inc.`, `Lathos` и `Laîhes` вместо `Lathes`).  Ложных тревог ноль.

**Но выдуманное `.0005` не помечено.**  И не могло быть: галлюцинация по
определению высоковероятна — она заполняет пробел самым правдоподобным, а не
случайным.  Logprob измеряет уверенность в продолжении, а не в прочтении.
Разница между этими двумя величинами и есть то, чего в модели нет по устройству.

### Самосогласованность

Три чтения того же PDF при `temperature=0.4` (`tools/selfcons.py`).  Из 270
ячеек одинаковы во всех трёх 217, то есть 80 %.  А расходятся они не где
попало:

| страница | совпало ячеек | чем известна |
|---|---|---|
| 304 | **2 из 23** | здесь выдумано значение допуска |
| 313 | 23 из 43 | здесь склейка двух таблиц поперёк колонок |
| 303 | 8 из 14 | здесь потерян знак ± |

Три чтения стр. 304 дают `.0005 / .0006 / .0007`, потом `.0005 / .0005 / .0005`,
потом снова `.0005 / .0005 / .0005`; заголовок пляшет между `20" to 31"` и
`20" to 34"`, `Lakes` / `Laths`.  Ни одно чтение не верно, но **сама
неустойчивость и есть сигнал**: две страницы, которые мы весь день находили
руками, оказались первыми двумя по неустойчивости.

Вывод: самосогласованность ловит то, чего вероятности не ловят, и стоит
троекратного счёта — но только по табличным кропам, а это малая доля вызовов.

## Проба на выдумывание: можно ли побороть галлюцинацию

Повод — довод, что сеть в 0.9B не должна «угадывать смысл чисел»: у неё нет
знаний о мире, которыми большая модель могла бы додумать.  Значит, достраивает
она узор, а не смысл.  Проверено четырьмя подачами одного промпта по спорной
ячейке стр. 304 (`PROBE=1`, `_probe_hallucination`).

- **Пустой белый лист.**  Модель выдаёт полноценные таблицы — китайские
  канцелярские шаблоны (`项目名称 | 内容 | 发布日期`), пять разных за пять
  попыток.  Значит, сочинять из ничего она готова.  Но сочиняет чужое, не наше:
  наше `.0005` не чистый языковой навык, картинка на него влияла.
- **Только правая треть.**  Пять попыток — пять разных бессмыслиц (`20\' to 24\'
  (a.d.`, `"A" to "A"`).  Столбец объективно нечитаем этой моделью.
- **Левые две трети.**  Убрав третий столбец, модель прочла второй как
  `12" to 15" Inc.` — верно (совпадает с Mistral).  С полным контекстом читала
  `18"`.  **Контекст портит чтение**: соседний узор перебивает картинку.
- **Разрешение.**  На 576 dpi (`PROBE_SCALE=8`) стало хуже, чем на 288:
  `U to .0005"` вместо `0 to`, `.0606` вместо `.0005`.  Оптимум подачи — около
  разрешения, на котором модель обучалась, а не родного разрешения скана.
  Ранее записанный вывод «мы сами уменьшаем картинку» верен только до 288 dpi.

Чернила при этом на месте: на 864 dpi ячейка читается глазом как `0 to .0015"`,
и Mistral её прочёл.  То есть информация есть, а наша модель её не берёт ни при
каком разрешении.

Вывод, поправляющий более ранний.  Сказанное про калиброванность верно: вес не
покупает умения сомневаться (у olmOCR 7B выдуманных чисел вшестеро больше).  Но
я смешал это с разборчивостью, а это разное: на выцветшем начертании ёмкость
как раз решает — Mistral прочёл, мы нет.  Систематические промахи на этой
типографике (`Laths` вместо `Lathes`, `mch`/`mth` вместо `inch`) — ровно тот
разряд ошибок, который лечится дообучением на 539 страницах одной книги.

Итог по галлюцинациям: устранить нельзя, обнаружить можно надёжно (изоляция
столбца плюс пересэмплирование даёт 5 разных ответов из 5).  А убрать контекст
— дёшево и, судя по второму столбцу, полезно само по себе.
