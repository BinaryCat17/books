# vast.ai: грабли и замеры

Всё, что стоило денег или часов. Часть исправлена переездом на SDK — отмечено.

## Исправлено переходом с CLI на SDK

**`destroy instance` требовал подтверждения и при отказе возвращал 0.**
Самая дорогая ловушка: неинтерактивный вызов печатал `Aborted`, код возврата 0,
инстанс продолжал работать, а скрипт рапортовал об уничтожении. В SDK
`destroy_instance(id)` ничего не спрашивает. Проверку повторным запросом мы
всё равно оставили — она стоит один вызов.

**`vastai execute` не годится для произвольных команд.** Это не «ещё один ssh»:
в справке прямо написано «Execute a **(constrained)** remote command», список
разрешённого — `ls`, `rm`, `du`. Всё остальное отвечает `400: Invalid command
given`. Проверено по исходнику, не по документации.

**Разбор stdout вместо структур.** Ошибки были строками, формат вывода CLI
никак не версионирован.

## Остаётся актуальным

**Ключ, зарегистрированный на аккаунте, в инстанс не попадает.**
`create ssh-key` кладёт его только в аккаунт. Нужен `attach_ssh` для **каждого**
инстанса, иначе `Permission denied (publickey)` — и узнаёшь ты об этом после
того, как выкачал шесть гигабайт образа.

**sshd загоняет вход в tmux и глотает команду.** `ssh host 'команда'` печатает
`no sessions / open terminal failed` и не выполняет ничего. Лечится
`touch /root/.no_auto_tmux` в onstart.

**Без `cancel_unavail=True` неудачное размещение создаёт остановленный
инстанс**, который продолжает брать деньги за диск. Диск стоит по медиане
$0.20 за ГБ-месяц: 60 ГБ — около $12 в месяц ни за что.

**`ssh_host` заполняется не всегда**, хотя `ssh_url` при этом отвечает
нормально. Ждать его в цикле — значит молча висеть до таймаута.

**У образов бывает нет `/workspace`.** Не полагайся, создавай свой каталог.

**`pkill -f` ловит собственную оболочку** и роняет скрипт с кодом 144.
Убивать только по сохранённому PID.

**Сетевых томов на рынке нет.** `create_network_volume` в API есть,
`search_network_volumes()` возвращает **ноль офферов**. Локальные тома прибиты
к физической машине. Персистентного кеша весов не будет.

## Что внутри официального образа

Прочитано из config-блоба зеркала, история совпадает 1:1 с 15 слоями манифеста.

| # | сжато | что это |
|---|---|---|
| 0–7 | 0.49 ГБ | debian bookworm + Python 3.10.16 + libgl/шрифты |
| **8** | **3.69 ГБ** | `pip install paddlepaddle-gpu==3.2.1`, индекс **cu126** |

Отсюда три вывода:

1. **torch и vllm отсутствуют вовсе** — поэтому VLM считался в процессе.
   При этом внутрь положен `pipeline_config_vllm.yaml`, и CMD по умолчанию
   рассчитан на **внешний** сервер vLLM.
2. Монолит 3.69 ГБ — это paddlepaddle-gpu с вшитой CUDA 12.6. Индекс `cu126`

3. Веса — 1.54 ГБ, 26% образа. Вынести их на HF полезно, но само по себе
   холодный старт это не лечит.

## Чего нельзя добиться в принципе

Демоном docker на арендованном хосте мы не управляем, поэтому:

- ленивая подгрузка (eStargz, SOCI, nydus) недоступна — это плагин демона;
- `zstd:chunked` docker не умеет тянуть частично;
- параллельной докачки **внутри** слоя нет ни в одной версии docker;
- `max-concurrent-downloads` — настройка хоста, не наша.

**Единственный доступный рычаг — раскладка слоёв в собственном образе.**

## Замер: детекция макета на CPU (18.08.2026)

Соблазн был очевидный: сам VLM считает vLLM на карте, а paddle нужен только
детекции макета — значит можно взять CPU-колесо на 186 МБ вместо GPU-шного на
3.69 ГБ и уполовинить образ.

Замер на реальных страницах книги (`bench/test25.pdf`, 150 dpi, 16 ядер),
модель `PP-DocLayoutV2` — та самая, что прописана в `PaddleOCR-VL.yaml`:

| конфигурация | с/страница | 539 страниц |
|---|---|---|
| по умолчанию | 7.59 | 68 мин |
| MKLDNN + 16 потоков | **9.71** | 87 мин |
| MKLDNN + 8 потоков | 8.26 | 74 мин |

Многопоточность делает **хуже**. Против ~8 минут работы самого VLM на карте.

Полная стоимость книги при $0.378/час:

| | образ | доставка | детекция | VLM | итого |
|---|---|---|---|---|---|
| paddle CPU | 5 ГБ | 2.7 мин | 59 мин | 8 мин | 71 мин = **$0.449** |
| paddle GPU | 9 ГБ | 4.9 мин | 1 мин | 8 мин | 15 мин = **$0.097** |

Экономия четырёх гигабайт образа оборачивается лишним часом аренды.
Первый вывод был: только GPU-сборка paddle. Он продержался недолго.

## Замер: тот же макет через ONNX Runtime (18.08.2026)

Оказалось, что paddle для детекции не нужен вовсе. У PaddlePaddle **37
официальных ONNX-репозиториев** — макет, ориентация, PP-OCRv5/v6, формулы;
`PaddlePaddle/PP-DocLayoutV2_onnx` обновлён 10 июня, то есть новее paddle-весов.
Для самой VL-модели ONNX нет вовсе: там GGUF и vLLM. Граница проходит ровно
между статическим графом и авторегрессионной генерацией с KV-кешем.

Тот же процессор, те же пять страниц, 82 рамки:

| движок | с/страница |
|---|---|
| paddle (CPU) | 8.59 |
| **ONNX Runtime (CPU)** | **2.45** |

Сравнение выхода — по сопоставлению рамок через IoU, а не по позиции в списке
(порядок у движков разный, и наивное сравнение давало ложные 662 пикселя):

```
рамок постранично:   [25, 20, 6, 19, 12]  в обоих движках
сопоставлено IoU>0.9: 82/82 (100%)
худший IoU: 1.0000    средний: 1.0000
макс. расхождение координат после сортировки: 0.00 пикселя
```

Расхождения нет вообще. Экспорт в ONNX — перезапись графа, а не пересчёт
весов: официальные ONNX-веса весят 204.1 МБ против 203.9 МБ у paddle,
совпадение размера и означает конвертацию без квантования. Квантованные
версии на HF есть (uint8) — вот их брать нельзя.

**Итоговый вывод: детекция на ONNX Runtime, paddle только CPU-каркасом.**

| | образ | крупнейший слой | стеки CUDA |
|---|---|---|---|
| paddle GPU | ~9 ГБ | 3.69 ГБ (41%) | cu126 + cu13 |
| **ONNX** | **~6 ГБ** | ~1.5 ГБ (25%) | только cu13 |

`onnxruntime-gpu` 1.29 зависит от `nvidia-cuda-runtime~=13.0` и
`nvidia-cudnn-cu13` — тот же стек, что приносит torch, поэтому уходит и
сожительство двух поколений CUDA в одном контейнере.

Включается ключом `engine: onnxruntime` в подмодуле `LayoutDetection`
конфига paddlex (у одноуровневого `engine` наивысший приоритет), конфиг
пробрасывается в `PaddleOCRVL(paddlex_config=...)` через `**kwargs`.

## Доставка: docker против всего остального (замерено 19.08.2026)

Главный вывод: **docker — самый медленный способ положить байты на машину**,
и обойти это его настройками нельзя, потому что демон на арендованном хосте
не наш.

| | образ через docker | окружение мимо docker |
|---|---|---|
| объём | 6.02 ГБ | ~11 ГБ |
| время | 10.7 мин | 82 с |
| скорость | 76 Мбит/с | ~1100 Мбит/с |

Обе строки — RTX 4090, канал хоста 1518 Мбит/с, NVMe 8166 МБ/с.

Почему 76: docker качает три слоя одновременно, внутри слоя ровно одно
HTTP-соединение, а реестр режет соединение. Проверено отдельно на том же
blob'е: 1 поток — 11 Мбит/с, 3 потока — 31, то есть **ровно втрое**. Душат
соединение, а не полосу. Раскладка слоёв упирается в тот же потолок:
дробление 9.2 ГБ / 46% на 6.02 ГБ / 23% ускорило вдвое и на этом кончилось.

Распаковка — вторая беда: слои накладываются строго по одному, gzip внутри
слоя однопоточный. После "Download complete" прошло ещё девять минут при
диске 8166 МБ/с. То есть 11 МБ/с по сжатому входу, и диск ни при чём.

Образ на 54 МБ поднимается за 31 секунду. Отсюда вся конструкция.

## Грабли vast, найденные при переезде на тонкий образ

**vast достраивает любой образ своим слоем с ssh.** В логе это видно как
сборка `<образ>_<тег>/ssh`. Своего sshd в образе держать не надо — он мешает:
демон поднимется наш, а ключи vast положит в свой authorized_keys.

**Достройка кешируется по имени с тегом.** Неизменный `latest` означает, что
на машине навсегда останется сборка от старой версии базы. Тег обязан меняться
с каждой сборкой — у нас это короткий SHA коммита.

**Ключ отвергается при верном ключе.** `Permission denied (publickey)`, а в
логах контейнера: `Authentication refused: bad ownership or modes for file
/root/.ssh/authorized_keys`. vast кладёт файл с чужим владельцем (у нас было
`115:1002`). Лечится `StrictModes no` в образе плюс `chmod` в фоне из onstart —
второе важно, потому что первое не доедет на машине с кешированной достройкой.

**Прокси `sshN.vast.ai` иногда не поднимает туннель**: `remote port forwarding
failed for listen port`. Прямой порт при этом отвечает. Ходим на прямой адрес,
прокси — запасной.

**Логи контейнера доступны через API** (`v.logs(instance_id=...)`) и содержат
вывод sshd. Когда ssh не пускает, это единственный способ узнать почему.

## Чего не хватает чистому Debian для этого стека

- `libgl1`, `libglib2.0-0` — иначе `ImportError: libGL.so.1` на импорте cv2,
  который paddlex тянет безусловно;
- `libgomp1` — OpenMP для numpy и paddle;
- `gcc`, `g++`, `libc6-dev` — triton и flashinfer компилируют ядра на лету.
  Одного gcc мало: ядра на C++, nvcc падает на `cannot execute cc1plus`;
- `CUDA_HOME` — flashinfer ищет CUDA по нему, иначе по `/usr/local/cuda`,
  которого нет: CUDA приезжает колёсами (`nvidia/cu13/bin/nvcc`).

## Стыки vLLM и paddleocr

**`vl_rec_server_url` сам по себе ничего не переключает.** Нужен
`vl_rec_backend="vllm-server"`, иначе пайплайн строит локальную VL-модель и
падает на `gpu:0`, потому что paddle у нас CPU-сборки.

**`paddlex_config` словарём подменяет конфигурацию целиком, а не сливается.**
В `paddleocr/_pipelines/base.py` это буквально `config = self._paddlex_config`.
Передать один подмодуль нельзя — пайплайн останется без `pipeline_name`.
Конфигурацию надо взять самому через `load_pipeline_config("PaddleOCR-VL-1.6")`
и слить свой подмодуль в неё.

**flashinfer не собирает сэмплер**: колесо `nvidia-cuda-nvcc` приезжает 13.3,
torch собран под CUDA 13.0, заголовки cccl это ловят. Проще выключить:
`VLLM_USE_FLASHINFER_SAMPLER=0` — заодно уходит компиляция ядер из старта.

**vLLM по умолчанию забирает 90% видеопамяти**, и детекции макета не остаётся:
ONNX Runtime падает на `Failed to allocate memory`. Ставим 0.75.

**Время старта vLLM гуляет вшестеро между машинами** — 65 с против 374 с на
одинаковых RTX 4090. Ни канал, ни диск этого не объясняют: время размазано по
импортам, компиляции и прогреву, то есть по процессору хоста.
